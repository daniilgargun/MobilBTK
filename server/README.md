# Сторож страницы расписания

Cloudflare Worker, который раз в 15 минут смотрит на страницу расписания
БТК и, когда она меняется, отправляет приложению одно сообщение FCM.

## Зачем

Уведомления об изменениях приложение строит само: качает страницу,
сравнивает с тем, что уже знает, оставляет только то, что касается
профиля пользователя. Ломалась не эта логика, а момент её запуска —
фоновую задачу Workmanager Android усыпляет, особенно на оболочке Samsung,
и проверка просто не выполнялась. Сообщение FCM с высоким приоритетом
пробивает Doze, поэтому проверку времени вынесли на сервер.

Сервер намеренно **не разбирает расписание и ничего о нём не знает**. Он
сообщает единственный факт: «страница изменилась». Разбор, сравнение и
фильтр по профилю остаются в приложении, в единственном экземпляре —
иначе при каждом изменении вёрстки сайта пришлось бы чинить два парсера
на двух языках.

Опрос по таймеру в приложении никуда не делся и остаётся запасным путём:
сообщение может не дойти, а сторож — не пережить смену бесплатных тарифов.

## Что хранится

В KV лежат две записи: хэш последней виденной страницы и кэш токена
доступа Google. Ни пользователей, ни устройств, ни токенов устройств —
рассылка идёт в тему FCM, на которую подписывается приложение, поэтому
серверу знать о них нечего.

## Хэш считается по таблице, а не по странице

Сайт колледжа работает на Joomla и подставляет в разметку `csrf.token`,
который меняется на каждом запросе. Хэш всей страницы поэтому отличается
всегда. Считается хэш области от первого `<table` до последнего
`</table>` — она стабильна и вдвое меньше страницы (67 КБ из 172).

Ровно та же ошибка была в приложении: `last_page_hash` не совпадал
никогда, и каждая фоновая синхронизация заново разбирала всю разметку.
`ParserService.scheduleRegion` и `src/page.ts` — зеркала друг друга,
правятся вместе.

## Текущее состояние

Развёрнуто и работает:

- отдельный аккаунт Cloudflare, не тот, где развёрнуто остальное;
- адрес `https://btk-schedule-watcher.btk-schedule-watcher.workers.dev`;
- расписание запусков и хранилище состояния созданы, страница читается,
  хэш совпадает с тем, что считает приложение.

**Не сделано:** не задан секрет `FCM_SERVICE_ACCOUNT`. Пока его нет,
сторож видит изменения, но не рассылает — `/check` отвечает
`not-configured`, и хэш в этом случае намеренно не запоминается, чтобы
изменение не пропало. Как получить ключ — шаг 2 ниже.

## Развёртывание

Воркер живёт на **отдельном аккаунте Cloudflare**. Ни идентификатора
аккаунта, ни ключей в репозитории нет: всё передаётся переменными
окружения, поэтому `wrangler login` на рабочей машине не переключается и
основной аккаунт не затрагивается.

### 1. Аккаунт Cloudflare

Завести отдельный аккаунт, затем в нём:

- **Account ID** — на главной странице аккаунта, в адресе панели
  (`dash.cloudflare.com/<account_id>`);
- **API-токен** — «My Profile» → «API Tokens» → «Create Token» →
  шаблон «Edit Cloudflare Workers». Токену нужны права
  `Workers Scripts: Edit` и `Workers KV Storage: Edit`.

```bash
export CLOUDFLARE_ACCOUNT_ID=...
export CLOUDFLARE_API_TOKEN=...
```

Либо, если удобнее обычный `wrangler login`, — **в отдельной папке
настроек**, чтобы вход в основной аккаунт не сбивался:

```bash
export XDG_CONFIG_HOME="$HOME/.config-btk-watcher"
npx wrangler login    # в браузере должен быть открыт аккаунт сторожа
```

Эту переменную надо выставлять перед каждой командой wrangler для сторожа.
Без неё wrangler возьмёт вход основного аккаунта и ответит `401
Unauthorized` — идентификаторы-то в `wrangler.toml` от другого аккаунта.

### 2. Ключ Firebase

Firebase Console → «Настройки проекта» → «Сервисные аккаунты» →
«Создать новый закрытый ключ». Скачается JSON.

**Этот файл нельзя коммитить.** В истории репозитория уже был один
утёкший ключ; второго раза быть не должно.

Из того же экрана нужен **Project ID** — он же в
`android/app/google-services.json`.

### 3. Настройка

В `wrangler.toml` заменить `FIREBASE_PROJECT_ID = "REPLACE_ME"` на
настоящий идентификатор проекта.

Создать хранилище состояния и вписать полученный идентификатор вместо
`id = "REPLACE_ME"`:

```bash
cd server
npm install
npx wrangler kv namespace create STATE
```

Задать пароль ручной проверки — без него точка входа `/check` выключена,
иначе любой желающий мог бы дёргать ею сайт колледжа:

```bash
npx wrangler secret put CHECK_TOKEN
```

Положить ключ сервисного аккаунта в секреты (целиком, как есть):

```bash
npx wrangler secret put FCM_SERVICE_ACCOUNT < /путь/к/ключу.json
```

### 4. Запуск

```bash
npm run typecheck && npm test
npm run deploy
```

Проверить, не дожидаясь следующего запуска по расписанию:

```bash
curl 'https://btk-schedule-watcher.<поддомен>.workers.dev/check?token=<CHECK_TOKEN>'
```

Первый ответ будет `{"status":"first-run"}` — сравнивать не с чем,
сообщение не отправляется, иначе всем пользователям пришло бы
«расписание изменилось» просто потому, что сервер поднялся. Дальше:

- `unchanged` — страница та же;
- `notified` — изменилась, сообщение разослано;
- `not-configured` — изменилась, но ключ Firebase не задан;
- `download-failed` — сайт колледжа не ответил. Разовые пятисотки от
  bartc.by случаются, следующий запуск повторит попытку.

Что было раньше — `/state`:

```bash
curl 'https://btk-schedule-watcher.<поддомен>.workers.dev/state?token=<CHECK_TOKEN>'
```

Отдаёт последний запуск по расписанию, последний отказ сайта (с кодом и
куском ответа) и запомненный хэш. Сайт колледжа при этом не трогает.

Это единственный способ разобраться задним числом: логи воркера живут
считаные минуты и смотреть их можно только вживую, а вопрос «почему сегодня
не пришло уведомление» возникает через несколько часов. По `lastRun` видно
главное — идут ли запуски вообще; «запуски идут, но сайт не отвечает» и
«запусков нет» лечатся совершенно по-разному.

Живой лог: `npm run tail`.

### 5. Включить в приложении

В Firebase Remote Config выставить `push_enabled = true`. Приложение
подпишется на тему при следующем запуске.

Этот же ключ выключает подписку без выпуска новой версии — например,
если сторож перестанет работать. Приложение вернётся к опросу по таймеру.

## Расписание запусков

`*/15 4-18 * * 1-6` — раз в 15 минут, 07:00–21:00 по Минску, кроме
воскресенья. В cron время UTC, Минск круглый год UTC+3 без перевода
часов, поэтому окно смещено на три часа назад, а дни недели не съезжают.

Окно то же, что у фоновой синхронизации в приложении.

## Расход бесплатного плана

Один запуск — три подзапроса в худшем случае: страница, обмен токена
(раз в час), отправка FCM. Около 60 запусков в сутки. Записей в KV —
одна на изменение расписания плюс одна на обновление токена в час.
До лимитов бесплатного плана (100 000 запросов и 1000 записей в KV
в сутки) далеко.
